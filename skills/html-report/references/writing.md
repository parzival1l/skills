# Write the text

All text on the page follows ASD-STE100 Simplified Technical English (STE), in its pragmatic form. STE is the controlled language for aerospace maintenance manuals. It keeps each sentence clear to a tired reader whose first language is not English. Domain words stay as they are: "OCR", "idempotent", "p95", "LiteParse".

## Headings

- Write each heading as one full sentence, with a subject and a verb. It states a finding.
- Do not put a period at the end of a heading.
- Do not write fragment pairs. These are wrong: "Real pages. Real variety.", "More shapes. Same evidence.", "Evidence in. Guarantees out."
- Use sentence case. Use 12 words or fewer.
- Use the real numbers in the heading when you have them.

| Wrong | Right |
|---|---|
| Broader layouts. Same fidelity. | The new contracts accept more table layouts and keep every check |
| One cut too many. | Reader v2 adds one extra boundary in one packet |
| Confirmation alone is insufficient. | A "confirmed" answer does not pass the gate without evidence |
| Small study. Open notebook. | How we measured these results |

## Sentences

- Use 25 words or fewer for a description. Use 20 words or fewer for an instruction.
- Give one fact in each sentence. Give one topic in each paragraph, with six sentences or fewer.
- Use the active voice. Name the actor: "Reader v2 adds a boundary", not "a boundary is added".
- Use the simple present tense for results that the page shows.
- Use "can", "must", and "will". Do not use "should", "may", "might", "could", or "would".
- Keep the articles and the word "that". Do not write in telegraph style.
- Do not use semicolons. Write two sentences.
- Write "for example", not "e.g.". Write "that is", not "i.e.". Do not write "etc.".

## Words

- Use one word for one meaning. If the page says "rule", it never says "contract", "policy", or "law" for the same thing.
- Use plain words: "use", not "utilize". "Start", not "initiate". "Show", not "demonstrate".
- Do not use a noun phrase of more than three words. Write "the timeout for the pool", not "the pool timeout configuration value".
- Explain each project term once, at its first use.
- Do not invent labels. A tag such as "SHARED LOGIC / NO DOCUMENT EXEMPTIONS" means nothing to a new reader. Write a short fact: "Same rules for every document".

## Labels, tags, and notes

- Use the mono uppercase eyebrow for a short section name only: "Results", "Method", "Task 1".
- A tag states one fact in plain words: "21 rules, all proposed", "60 of 60 tasks".
- A note gives information. It never gives an instruction.
- Put a limit next to the claim that it limits. Do not collect all limits in one place.
- If a number needs a disclaimer, remove the number. Do not show the number with an apology.

## Numbers

- Show both sides of a comparison: "23 of 24", not only "96%".
- Write the unit after every number: "142 ms", "4.1¢".
- Copy every number from a source file. Never estimate.

## Self-check before you build

1. Read each heading. Is it one full sentence without a final period?
2. Read each tag and eyebrow. Can a new reader understand it?
3. Count the words in the longest sentence. Is the count 25 or fewer?
4. Search the page for "should", "may", "might", "could", "would", ";", "e.g.", "i.e.", and "etc.".
5. Look for two words that name one thing. Keep one of them.
